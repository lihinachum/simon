# ARCHITECTURE — Simon | משחק זיכרון עם אורות וצלילים

> מסמך ארכיטקטורה טכנית מבוסס על `PRD.md`. עודכן: 20 באוקטובר 2026. כל נוסחי ממשק המשתמש בעברית ובכיווניות RTL.

## 1. Technology Stack שנבחר

| תחום | טכנולוגיה | תפקיד |
|---|---|---|
| UI | **React** עם **TypeScript** | שני המסכים, לוח המשחק, משוב והצגת נתונים; בדיקות טיפוסים |
| Build ושרת פיתוח | **Vite** | פיתוח מקומי מהיר ובניית אתר סטטי ל־`dist/` |
| עיצוב | **CSS רגיל + SVG** | פריסה Mobile-first, ארבעה רבעי מעגל, הדגשות ואנימציית ניצחון |
| ניהול מצב | **React Hooks** (`useReducer`, `useEffect`, `useRef`) | State Machine של המשחק, מצבי ממשק ותיאום הפעולות; ללא ספריית State נוספת |
| יצירת אקראיות | **Web Crypto API** (`crypto.getRandomValues`) | בחירה בלתי מוטה של צבע חדש לכל שלב, ללא AI |
| שמע | **Web Audio API** | ארבעה צלילים מובחנים, צליל שגיאה וצליל ניצחון; ללא קובצי שמע או שירות חיצוני |
| ניקוד קבוע | **Web Storage / `localStorage`** | שמירת השיא האישי ותוצאת המשחק האחרון בלבד |
| התקנה ועבודה כ־PWA | **vite-plugin-pwa** (מבוסס Workbox) | Web App Manifest, Service Worker, קובצי אפליקציה זמינים גם ללא חיבור לאחר התקנה/טעינה מוצלחת |
| בדיקות יחידה | **Vitest** | בדיקות חוקי המשחק, מעבר מצבים וניקוד |
| בדיקות חוויית משתמש | **Playwright** | בדיקות זרימות ובקרת ממשק בממדי מובייל; בדיקות ידניות בטלפונים אמיתיים לשמע, PWA והתנהגות רקע |
| ניהול קוד | **Git + GitHub Repository** | מקור האמת לקוד, קובצי תצורה ומסמכי המוצר |
| CI/CD ו־Hosting | **GitHub Actions + GitHub Pages** | בדיקות, Build ופריסה אוטומטית של קבצים סטטיים ב־HTTPS |

**לא נבחרו, מכיוון שאינם נדרשים:** Backend, API Server, Database, Authentication, Cloud Storage, Analytics, שירות AI, ספריית Routing, ספריית UI גדולה, ספריית State חיצונית, SSR ו־Supabase. אין צורך ב־Database Migrations או בסביבות Supabase.

### 1.1 הנימוקים לבחירה

- **React + TypeScript**: שילוב Mainstream בעל תיעוד נרחב ודוגמאות רבות לכלי AI; מספק רכיבים מבודדים וניהול מצב בלי שכבת שרת. נבחנו גם Vue ו־Vanilla TypeScript. Vanilla יכול להיות קטן יותר, אך React נבחר בזכות המערכת האקולוגית, איכות תיעוד ה־State ושימושיות לתחזוקה. **אין להשתמש ב־Next.js**: SSR ושרת אינם תורמים למוצר.
- **Vite**: תהליך Build פשוט לאתר סטטי. נבחן מול Parcel והגשה של HTML/JS ללא Build; TypeScript, אינטגרציית PWA ו־GitHub Actions הופכים את Vite לפתרון הישיר.
- **CSS + SVG**: אין צורך ב־Tailwind או בספריית רכיבים לצורך שני מסכים ולוח ייחודי; SVG מאפשר לוח רבעי מעגל חד גם במסכים קטנים. כל רבע הוא אלמנט אינטראקטיבי נגיש עם אזור מגע מתאים.
- **Web Audio API**: מאפשר ליצור את הצלילים בדפדפן ללא קבצי MP3 ובלי ספרייה כדוגמת Tone.js. נבחנה גם אפשרות `<audio>`/קובצי שמע; סינתזה פשוטה מספיקה לארבעה טונים ולאפקטי סיום.
- **GitHub Pages**: משרת קבצים סטטיים ב־HTTPS, מתאים במדויק למערכת Frontend-only, ומאפשר Build ופריסה אוטומטיים מתוך GitHub Actions. נבחנו גם Cloudflare Pages ו־Netlify, אך אין הצדקה למעבר מהעדפת ה־Hosting שנקבעה.
- **PWA**: תוסף Vite בשל עם `generateSW`, ללא כתיבת Service Worker מותאם מאפס. Offlining הוא אופן מימוש של PWA, לא מסך או יכולת מוצר חדשה.
- **Vitest + Playwright**: מניעת רגרסיות בלוגיקה של רצפים, מעברים והפרעות למגע. אין צורך בשירות בדיקות חיצוני.

### 1.2 מגבלות וסיכונים

1. **שמע במובייל**: דפדפנים יכולים למנוע השמעה לפני אינטראקציית משתמש או לאחר חזרה מרקע. יש ליצור/להפעיל `AudioContext` בעקבות הלחיצה על **"התחל"** ולנסות `resume()` בחזרה למצב פעיל או לאחר נגיעה נוספת, בלי להניח שהפעלת שמע תצליח. אין כפתור השתקה בהתאם ל־PRD.
2. **שהיה לעומת סגירת אפליקציה**: חזרה מאפליקציה אחרת תאפשר המשך כל עוד דף המשחק נשאר בזיכרון. מערכת ההפעלה עלולה לסגור דף/PWA ברקע; במקרה כזה תתבצע טעינה חדשה והמשחק יתאפס, כמשמעות אי־שמירת משחק פעיל. לא ניתן להבטיח המשכיות לאחר סגירה על ידי מערכת ההפעלה בלי לשנות את ה־PRD.
3. **נתוני Local Storage**: שייכים לדפדפן ול־Origin. עשויים להימחק בהגדרות הדפדפן, בגלישה פרטית או בהסרת האפליקציה; התקנה כ־PWA אינה מבטיחה שיתוף נתונים עם דפדפן אחר. אין סנכרון.
4. **PWA**: אפשרויות התקנה ויכולות Service Worker שונות בין דפדפנים וגרסאות מערכת. יש לבדוק ידנית ב־Android וב־iOS. טעינה ראשונה דורשת רשת; עדכון גרסה עשוי להתעכב עד לטעינה מחדש.
5. **Hosting**: GitHub Pages מיועד לאתרים סטטיים; הוא אינו מספק Backend, כללי Routing של SPA או שליטה חופשית בכותרות HTTP. המערכת תשתמש בשני מסכים באותו מסמך ללא נתיבי שרת, כדי למנוע שגיאת 404 בטעינה ישירה.
6. **עלויות**: אתר קטן ב־GitHub Pages צפוי להתאים לשימוש חינמי במסגרת המכסות והתנאים של GitHub. במאגר פרטי זכאות Pages ומכסות Actions תלויות בתוכנית החשבון. יש לוודא תנאים בעת יצירת המאגר; דומיין מותאם אישית אינו נדרש ויכול לעלות כסף.

## 2. ארכיטקטורת המערכת

### 2.1 מבנה כללי

```text
GitHub Repository
  └─ GitHub Actions: test → build → deploy
                                  │
                                  ▼
                           GitHub Pages (HTTPS)
                                  │ static HTML/CSS/JS/Manifest/SW
                                  ▼
                     דפדפן / PWA מותקן במובייל
                       ┌──────────────────────┐
                       │ React UI             │
                       │ בית / משחק | אודות   │
                       └──────────┬───────────┘
                                  │
                       Game Controller / State
                         │       │       │
                         ▼       ▼       ▼
                     Web Audio  localStorage  Service Worker
                       API      ניקוד בלבד    Cache סטטי
```

כל הפעולות הלוגיות והנתונים הפרטיים של המשחק מתבצעים **בדפדפן המשתמש**. אין תקשורת בזמן משחק עם שרת אפליקטיבי ואין APIs חיצוניים. GitHub Pages מגיש קבצים סטטיים בלבד.

### 2.2 Modules ואחריות

| Module | אחריות | תלות עיקרית |
|---|---|---|
| **Application Shell** | הגדרת `lang="he"`, `dir="rtl"`, מטא־תגיות מובייל, החלפת מסך בית/אודות, רישום PWA | React |
| **Home / Simon Board** | ציור ארבעה רבעי מעגל SVG, אזור מרכזי עם "התחל"/מספר שלב, כפתור אודות, משוב הצלחה/סיום | מצב המשחק |
| **About Screen** | תיאור, הוראות, שיא אישי ותוצאה אחרונה, כפתור חזרה | Score Store |
| **Game Engine** | רצף קלאסי מתארך, השוואת לחיצות, התקדמות אוטומטית, ניצחון והפסד, ניקוד | מחולל אקראיות; Game State |
| **Sequence Player** | הדגמה בסדר קבוע, ההבהובים, שמע, השהיה וביטול פעולות ישנות | Game State; Audio Engine |
| **Audio Engine** | יצירת טונים לארבעת הצבעים ואפקטי סיום; טיפול בחסימת שמע/חזרת רקע | Web Audio API |
| **Score Store** | קריאה, אימות ושמירה של `bestScore` ו־`lastScore` | localStorage |
| **Visibility Controller** | ניטור חזרה/יציאה מרקע, השהיה, חידוש רצף או קלט | Page Visibility API; Game State |
| **PWA / Service Worker** | Cache לנכסים סטטיים בלבד, התנהגות התקנה ועדכון | vite-plugin-pwa |

חלוקה זו היא **לוגית** ולא מחייבת מבנה תיקיות או מספר Components מסוים. אין ליצור Layer של Backend או API מלאכותי.

### 2.3 Game State ו־State Machine

מצבי המשחק המומלצים:

- `idle`: טרם התחלת המשחק. במרכז הלוח כפתור **"התחל"**.
- `showingSequence`: הדגמת הרצף; כל לחיצות הצבע חסומות.
- `awaitingInput`: המשתמש משחזר את הרצף; אין Timeout.
- `levelSuccess`: הודעת הצלחה קצרה; הקלט חסום עד לשלב הבא.
- `paused`: הדף ברקע; שומרים בזיכרון את המצב שממנו הושהה והאם נקטעה הדגמה.
- `lost`: תוצאה סופית, צליל שגיאה והודעה עם כפתור **"משחק חדש"**.
- `won`: תוצאה 10, אפקטים חגיגיים והודעה עם כפתור **"משחק חדש"**.

מעברי מצב קובעים באופן יחיד מתי המשתמש יכול ללחוץ. הלחיצה על **"התחל"** או **"משחק חדש"** מאפסת את ה־Game State ומשתמשת ברצף אקראי חדש. ב־`showingSequence`, ב־`levelSuccess`, ב־`paused` ובמצבי סיום, אין לקבל קלט צבע.

**נתוני המשחק בזיכרון בלבד**:

| שדה לוגי | משמעות |
|---|---|
| `status` | מצב המשחק |
| `sequence` | מערך צבעים מתוך `blue`, `red`, `yellow`, `green` |
| `level` | השלב הנוכחי, 1 עד 10 בזמן משחק |
| `inputIndex` | אינדקס הצבע הבא שעל המשתמש לשחזר |
| `completedLevels` | 0 עד 10; הניקוד של המשחק הנוכחי |
| `pausedFrom` | המצב והקשר החידוש כאשר המשחק מושהה |
| `playbackToken` | מזהה סבב הדגמה לביטול פעולות Asynchronous שהתיישנו |

כל שלב באורך `level`: מתחילים ברצף באורך 1, ולאחר השלמה מוסיפים **צבע אחד בלבד** לסוף הרצף. השתמשו ב־`crypto.getRandomValues` ובדגימה בלתי מוטה של ערכים 0–3 (למשל שני הביטים התחתונים של Byte) לבחירת הצבע; אין צורך במחולל AI.

**כללי בדיקה אטומיים:**

1. לחיצה מאושרת רק ב־`awaitingInput` ולאחר השלמת טיפול בלחיצה הקודמת, כדי למנוע Double Tap, מצב Race והשמעות חופפות.
2. בלחיצה תקפה מוצגים הבהוב ונשמע הצליל של הצבע שנלחץ, ונבדקת התאמה ל־`sequence[inputIndex]`.
3. צבע שגוי גורם מיד ל־`lost`; הניקוד הוא `completedLevels` ולא מספר השלב שבו אירעה הטעות.
4. צבע נכון שאינו האחרון מקדם את `inputIndex`. בהשלמת רצף שלב שאינו 10, מעלים `completedLevels`, מציגים הצלחה קצרה, מוסיפים צבע, מאפסים אינדקס ומתחילים להציג את הרצף החדש.
5. בהשלמת שלב 10 מעלים `completedLevels` ל־10 ועוברים ל־`won`, ללא שלב 11.
6. סיום משחק מעדכן את Score Store **פעם אחת בלבד**; נטישה, ניווט לאודות ורענון לא מעדכנים אותו.
7. כל Timer, אנימציה או פעולה Asynchronous ניתנים לביטול על ידי שינוי `playbackToken` וניקוי משאבים. אסור שפעולה ישנה תעבור שלב או תנגן צליל לאחר איפוס.

### 2.4 הדגמת רצף, קצב ומשוב

- Sequence Player מנהל **הדגמה סדרתית יחידה**: הפעלת בהוב וצליל לכל צבע, כיבוי, מרווח קבוע ומעבר לצבע הבא. אותם זמני הדגמה נשמרים בכל השלבים; הם קבועי תצורה פנימיים ולא אפשרויות למשתמש.
- עם תום ההדגמה משתנה המצב ל־`awaitingInput` ומאפסים `inputIndex` ל־0.
- הפעלת צבע על ידי המשתמש משתמשת באותו זיהוי צבע, בהבהוב ובצליל ייחודי; יש למנוע חפיפה לא רצויה של אירועי Tap ושל צלילים.
- ב־CSS מסומן מצב פעיל גם באמצעות שינוי עוצמת/בהירות הצבע, מבלי להזיז את אזורי המגע. אנימציית ניצחון וצליל ניצחון הם אפקטי UI מקומיים; רצוי לכבד `prefers-reduced-motion` באמצעות חלופה חזותית מופחתת בלי לשנות את כללי המשחק.
- Audio Engine מייצר ארבעה צלילים יציבים, אחד לכל צבע, בעזרת Oscillator ו־GainNode עם Envelope קצר; בנוסף צליל טעות קצר וצליל ניצחון מובחן. יש למנוע עוצמת שמע חדה/Clipping ולשחרר Nodes בתום הצליל.

### 2.5 השהיה וחידוש

ה־Visibility Controller מאזין ל־`document.visibilitychange` ובודק `document.visibilityState`:

1. **בעת מעבר ל־`hidden`**: מבטלים פעולות הדגמה מתוזמנות, עוצרים צלילים פעילים ושומרים את מצב המשחק הפעיל **בזיכרון React בלבד**. אין כתיבה ל־Local Storage.
2. **אם נקטעה הדגמה**: בחזרה ל־`visible` מציגים מחדש את **כל הרצף של אותו שלב**, בלי להגריל אותו מחדש, ולאחריו מאפשרים קלט מהתחלה.
3. **אם נקטע שחזור משתמש**: בחזרה משחזרים `awaitingInput` עם אותו `inputIndex` ואותו רצף. אין Timeout ואין הצגה מחדש של ההדגמה.
4. **אם הושהה `levelSuccess`**: לא מתקדמים ברקע. בחזרה משלימים את הודעת ההצלחה ולאחריה את המעבר התקין לשלב הבא, בלי לדלג על הדגמה.
5. **חזרת שמע**: מנסים לחדש `AudioContext` בהתאם למדיניות הדפדפן. כאשר חידוש השמע נחסם, אין להריץ הדגמת רצף בלתי־שמיעה מתוך הנחה שהצלילים עובדים; ניתן להמתין לאינטראקציה המותרת הבאה, בלי להוסיף מסך מוצר או לבטל את המשחק.
6. **רענון/סגירה שמביאה לטעינה חדשה**: לא משחזרים משחק; נכנסים ל־`idle` ומציגים כפתור **"התחל"**.

מעבר למסך **אודות** הוא פעולה **שונה** מירידה לרקע: היא מבטלת משחק פעיל ומציגה מסך אודות; החזרה לבית מתחילה ב־`idle`. אין לבלבל בין שני האירועים.

### 2.6 Data Model ואחסון

**אין Database.** נשמרים שני ערכי ניקוד ב־`localStorage`, באותו Origin של האתר:

| מפתח מוצע | סוג | פירוש | תחום |
|---|---|---|---|
| `simon.bestScore` | מחרוזת המייצגת מספר שלם | שיא אישי מכל המשחקים שהסתיימו | 0–10 |
| `simon.lastScore` | מחרוזת המייצגת מספר שלם | תוצאה אחרונה של משחק שהסתיים | 0–10 |

- בתחילת האפליקציה ובכניסה למסך אודות קוראים את שני הנתונים באמצעות Score Store; ערך חסר יוצג כמצב **"אין עדיין תוצאה"** ולא כ־0.
- ערך קיים נחשב תקין רק אם הוא מספר שלם בין 0 ל־10. ערכים פגומים, חסומים או בלתי קריאים יוצגו כבלתי זמינים; אין להציג נתון לא אמין.
- בסיום משחק בלבד יש לעדכן `lastScore` בתוצאה, ולחשב `bestScore = max(bestScore, newScore)` כאשר קיים שיא תקין. בהיעדר שיא תקין, התוצאה החדשה הופכת לשיא.
- קריאות וכתיבות עטופות ב־`try/catch`; אם האחסון אינו זמין, המשחק ממשיך לפעול וה־UI לא מציג מצג שווא שהשמירה הושלמה. במקרה כזה ניתן להציג הודעת אי־זמינות מקומית.
- לא שומרים רצף, שלב נוכחי, `inputIndex`, נתוני שימוש או מידע אישי.
- במצב גלישה פרטית או לאחר ניקוי נתוני אתר, ערכים קודמים עשויים להיעלם.

### 2.7 ממשק, מסכים וניווט

- **בית/משחק**: כפתור **אודות** בחלק העליון; לוח Simon SVG של ארבעה רבעי מעגל עם התאמה למסך טלפון; מרכז הלוח מכיל **"התחל"** ב־`idle` ומספר שלב `x/10` בעת משחק. במצב סיום יש הודעה, תוצאה וכפתור **"משחק חדש"**.
- **אודות**: כפתור חזרה, הסבר קצר, הוראות משחק, תוצאת המשחק האחרון ושיא אישי. אין מסכים נוספים.
- מעבר המסכים מנוהל ב־React State בתוך אותו מסמך HTML; אין צורך ב־React Router או בכתובות URL שונות. ניווט לאודות באמצע משחק מבטל את ה־Game Engine ללא שמירת נתון.
- ב־HTML מוגדרים `lang="he"` ו־`dir="rtl"`. שמות צבעים, `aria-label`, הודעות ופקדים בעברית; שם המוצר **Simon** יכול להישאר בלועזית. יש להשתמש בכפתורים סמנטיים או ב־SVG עם נגישות מקבילה המאפשרת מגע, פוקוס ומקלדת, בלי להוסיף ממשק חדש.
- מידות לוח וזמינות פקדים נגזרות מרוחב/גובה חלון מובייל ומ־`safe-area-inset`. אין צורך בפריסות ייעודיות לטאבלט/מחשב.

### 2.8 PWA ו־Caching

- השתמשו ב־`vite-plugin-pwa` עם `generateSW` ליצירת Web App Manifest ו־Service Worker לאחר Build.
- Manifest כולל שם אפליקציה, שם מקוצר, `lang: he`, `dir: rtl`, `display: standalone`, `start_url` ו־`scope` התואמים ל־`base` של האתר, צבעי Theme ואייקונים בגדלים הנדרשים להתקנה (לפחות 192×192 ו־512×512, וכן נכסים נדרשים נוספים לפי הדפדפן).
- Precache לנכסי האפליקציה הסטטיים בלבד: HTML, JS, CSS, אייקונים ו־Manifest. אין בקשות Backend ואין Cache לנתוני משחק. מצב Offline זמין **לאחר** שהקבצים הנדרשים נשמרו בהצלחה.
- Service Worker לא שומר ניקוד; Local Storage נשאר מקור האמת היחיד לנתונים מקומיים.
- עדכוני Service Worker לא ירעננו בכוח משחק פעיל. יש להעדיף שימוש בגרסה החדשה בפתיחה/רענון הבא, כדי שלא לאבד התקדמות או ליצור ערבוב גרסאות.
- **GitHub Pages בפריסת Repository**: להגדיר `base: '/<REPOSITORY_NAME>/'` ב־Vite; התוסף, `start_url`, `scope` ונתיבי האייקונים חייבים לכבד את קידומת הפריסה. בדומיין מותאם אישית או אתר `username.github.io` בשורש: `base: '/'`.

### 2.9 Interfaces ו־Data Flows

לא נדרשים HTTP APIs, Authentication או אינטגרציות צד־שלישי. כל הממשקים כאן הם **ממשקים פנימיים בין Modules**:

- UI → Game Engine: `start`, `tap(color)`, `newGame`, `abandon`.
- Game Engine → Sequence Player: `play(sequence)`, `cancel`, `pause`.
- Sequence Player / UI → Audio Engine: `playColor(color)`, `playLoss`, `playWin`, `stop`.
- Game Engine → Score Store: `saveCompletedResult(score)` **רק** בהפסד/ניצחון.
- About Screen → Score Store: `getScores()`.
- Visibility Controller → Game Engine / Sequence Player: `pauseOnHide`, `resumeOnShow`.

**Flow — משחק רגיל:** לחיצת **"התחל"** → הפעלת AudioContext במחוות משתמש → יצירת צבע אקראי → הדגמת הרצף → קלט משתמש ובדיקת השוואה → הצלחה והרחבה אוטומטית או סיום ושמירת ניקוד → הצגת תוצאה/משחק חדש.

**Flow — אודות:** ניווט לאודות → ביטול משחק פעיל בזיכרון ללא עדכון ניקוד → קריאת הנתונים השמורים → הצגתם → חזרה לבית במצב התחלתי.

**Flow — פריסה:** Push ל־GitHub `main` → בדיקות/בדיקת טיפוסים → `vite build` → העלאת `dist/` → GitHub Pages מגיש גרסה סטטית למשתמשים.

### 2.10 אבטחה ופרטיות

- אין חשבונות משתמשים, סיסמאות, הרשאות עסקיות, Tokens, פרטי תשלום או מידע אישי.
- כל הלוגיקה בצד הלקוח; אין להתייחס לניקוד כאל נתון מהימן לתחרות בין משתמשים, משום שניתן לשנות Local Storage בקלות. זה תואם ל־PRD של שיא אישי מקומי בלבד.
- GitHub Pages מגיש ב־HTTPS. אין להכניס Secrets לקוד, ל־Commit או ל־Build Variables של Frontend; כל ערך המשולב ב־Bundle נחשף למשתמש.
- אין לשלוח ניקוד או פעולות משתמש לשרת, ל־Analytics או לשירות AI.
- השתמשו בתלויות מוכרות, בקובץ Lock מחויב ל־Git ובבדיקות עדכון תלויות. אין להכניס HTML לא מהימן או להריץ `eval`.
- ה־Service Worker מוגבל ל־Scope של האפליקציה; הוא לא שומר מידע נוסף על המשתמש.

## 3. GitHub, Hosting, Configuration ו־Deployment

### 3.1 GitHub Repository וסביבות

- **Repository אחד** מכיל Source Code, `PRD.md`, `ARCHITECTURE.md`, `package.json`, `package-lock.json`, תצורות Build/Tests ו־GitHub Actions Workflow.
- ענף `main` מייצג את קוד ה־Production; שינויים נבדקים בענף עבודה וניתן למזג לאחר בדיקות. זו המלצת ניהול קוד ולא תוספת לפיצ'רים.
- **Development**: שרת הפיתוח של Vite במחשב הפיתוח, כולל גישה לבדיקה מטלפון באותה רשת לפי הצורך. אין שרת Backend ואין סביבת ענן לפיתוח.
- **Production**: GitHub Pages מגיש את תיקיית `dist/` שנבנתה ב־CI. אין משתני סביבה סודיים לשום סביבה.
- לפריסה נדרשות הרשאות GitHub Actions לפרסם Pages (`contents: read`, `pages: write`, `id-token: write`); הן שייכות ל־Workflow ולא לקוד הדפדפן.

### 3.2 Build ופריסה אוטומטית

1. **GitHub Pages → Settings → Pages → Source: GitHub Actions**.
2. Workflow מופעל אוטומטית ב־Push אל `main`, ואפשר גם להפעילו ידנית דרך GitHub Actions.
3. הורדת קוד, Node.js LTS, `npm ci`, בדיקת TypeScript, בדיקות Vitest, `npm run build`. בדיקות Playwright רצות ב־CI לפי תצורה כדי לוודא את הזרימות המרכזיות לפני פריסה.
4. פרסום Artifact מתיקיית `dist/` באמצעות GitHub Pages Actions הרשמיות. רק אם הבדיקות וה־Build הצליחו מופעל Deployment לסביבת `github-pages`.
5. Pages מפרסם את האתר בכתובת HTTPS. אין העלאה ידנית של קבצים בכל שינוי.
6. לאחר פריסה יש לבדוק זמינות קובצי Build, קידומת `base`, Manifest, טעינת Service Worker, מסכי המשחק וזרימת שמירת הניקוד.

**תצורה חשובה:** `base` חייב להתאים לכתובת GitHub Pages בפועל. שימוש בנתיבי Root שגויים ימנע טעינת JS או התקנת PWA בפרויקט תחת תת־נתיב.

### 3.3 עלויות ותפעול

- אין ספקי Backend, Database, Storage או AI בתשלום.
- GitHub Pages ו־GitHub Actions יכולים להספיק ללא עלות שוטפת באתר קטן בכפוף לתנאי החשבון והמכסות. מומלץ Repository ציבורי בחשבון GitHub Free אם אין צורך לשמור את הקוד פרטי; תנאי Pages למאגרים פרטיים משתנים לפי תוכנית.
- GitHub מציין מגבלת אתר של 1GB, מגבלת רוחב פס רכה של 100GB לחודש ומגבלות Deployment; אלה גבוהות מהצרכים הצפויים של משחק קטן, אך אינן התחייבות לזמינות ללא גבול.
- אין צורך בתחזוקת שרת, בגיבוי Database, ב־Migrations או במפתחות API.

## 5. בדיקות ואיכות

- **Unit Tests (Vitest)**: רצף באורך שלב, הוספת צבע יחיד, השלמה, טעות בשלב 1 וניקוד 0, הפסד בשלב 5 וניקוד 4, ניצחון בשלב 10, כתיבה אחת בלבד של תוצאת משחק שסוים, שמירה על שיא גבוה, היעדר כתיבה בהשהיה/נטישה, התנהגות מול Storage פגום או חסום.
- **UI/Flow Tests (Playwright)**: ניווט בין שני המסכים; איסור מגע בזמן הדגמה; מעבר אוטומטי; הודעות סיום ומשחק חדש; RTL ותצוגת מובייל. לשליטה בבדיקות לוגיקה אקראית אפשר להזריק מחולל צבעים דטרמיניסטי **בבדיקות בלבד**, בעוד שה־Production אקראי תמיד.
- **בדיקות ידניות חיוניות בטלפון אמיתי**: עוצמה ותזמון שמע ב־Safari/iOS ו־Chrome/Android; מחוות שמע; התקנת PWA, Offline לאחר טעינה ראשונה, מעבר לאפליקציה אחרת ונעילה, חזרה באמצע הדגמה ואמצע שחזור; פתיחת האתר אחרי סגירה מלאה; דיוק אזורי המגע והבהובים.
- **בדיקת פריסה**: טעינת האתר ב־GitHub Pages תחת תת־נתיב, תקינות אייקונים ו־Manifest, נגישות לאחר עדכון Service Worker, ונתונים מקומיים הנשארים בין רענונים.
